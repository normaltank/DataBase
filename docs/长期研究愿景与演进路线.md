## 1. 我们要建成什么

建设一个中心成员可以共同积累资料、辨识作者与来源、比较观点、追溯证据并形成研究成果的平台。资料库提供持续使用的数据基础；作者、期刊和机构成为可以长期研究的对象；研究判断与所依据的材料保持联系。

发展过程是：**资料积累 → 作者与来源关联 → 围绕问题整理证据 → 定性研究与分维度评价 → 形成可追溯成果**。中文阅读与检索贯穿其中，同时保留原文、原名和译文版本。

拉脱维亚资料用于先跑通真实研究流程，未来可扩展到其他国家、语言和议题。

后续取舍以 [研究质量与复核](../PRODUCT.md#研究质量与复核) 为条件：先用原件、真实问题和独立复核识别已有流程的困难，再据此决定需要的结构和自动化。2026-10-26 的只读盘点尚未发现真实库中的带出处摘录及报告引用；功能存在与真实研究使用分别评价，详见 [本轮核查记录](../work/研究复核深化验收.md)。

## 2. 用户已经确认的方向

- **作者、期刊、机构都要能研究。** 作者不能长期只是一行署名。应有能够持续整理信息、关联作品和形成研究积累的独立档案；期刊和机构在现有身份基础上继续发展。
- **定性研究是主要用途之一。** 能够整理研究主题、观点及其变化，比较不同作者、机构和期刊，并把判断联系到具体材料。具体研究分类和方法随后按实际课题细化。
- **影响力分两类评价。** 学术影响与政策／社会影响都需要，分别记录、分别评价，暂不合成一个总分。
- **中文为主，原文与译文并存。** 默认服务中文阅读和检索，保留原始内容、姓名、机构原名和出处，区分机器翻译与人工校订，保留译文版本。
- **自动积累，面向读者。** 最终系统应持续取得并整理来源文章，普通研究员以查看对象国新文章为主要体验，人工维护集中于异常；本轮已确认的收录、展示、身份及新增口径见 [PRODUCT](../PRODUCT.md#自采集自维护与对象国新文章2026-10-27-确认方向)。
- **数据库与写作分工。** 平台保存源数据和已经写好的报告，保留编辑、导入与导出，去掉专门的站内个人编译写作流程；资料夹用于收集内容和简短备注，研究资料与成品成果仍可供后续分析使用。早期研究写作示例保留其历史身份，新的使用与建设按 [R021](需求讨论记录.md#r021自采集自维护与前端重设计)及整体规格确认结果执行。
- **分批接入翻译服务。** 已有显式单篇 DeepSeek 题名／摘要翻译；新方向明确首批自动翻译题名与原文摘要、全文按需。生效规则与实现边界分别见 [PRODUCT](../PRODUCT.md#多语资料与中文使用2026-10-23-确认)和施工说明，不把方向当成已交付能力。
- **成果有依据，修改有责任。** 沿用资料关联、证据定位与版本保护；共同编辑和个人报告的作者授权例外按 [PRODUCT 第 3 节](../PRODUCT.md#3-已确认的共建规则)执行。

## 3. 研究人员未来应该能怎样使用

以下是帮助理解方向的示例，具体页面和字段仍由实施规格细化。

研究员读到一篇文章，点击作者后，可以查看已经确认属于此人的作品、姓名写法、相关机构，以及中心对其研究主题和观点的积累。遇到同名者，可以保留待确认的署名，避免把不同人的作品混在一起。

同一作者早年的文章署名机构 A，后来转入机构 B，两段经历及依据可以分别保留。当前任职信息不会改写旧文章发表时的署名事实。从期刊或机构进入，也能汇集相应作品、作者与研究笔记；“任职”“主办”“发布”“合作”各自有清楚含义。

研究员围绕一个具体问题，选取若干作者、期刊或机构及一个时期，比较主题、论点、证据和变化。平台帮助整理材料与已有发现，研究员形成判断，并记录哪些证据支持判断、哪些提出相反解释、哪些地方仍不足以下结论。

评价影响力时，能够分别查看学术贡献、引用和讨论，以及政策引用、机构采用或公共传播的证据。被提及、受到批评、被赞同和实际采用需要分别解释；本库收录量只说明本库覆盖情况，不能直接当作总体影响力。

读者可以在中文与原文之间切换，查看译文依据的原文版本及是否经过人工校订。原文更新或重新调用翻译服务时，已有人工修订与旧报告的引用依据仍能查回。

## 5. 当前建设顺序与后续建议

用户最新确认的优先级由 [PRODUCT 第 6 节](../PRODUCT.md#6-长期方向) 维护。以下以该顺序组织候选范围；原先优先推进评价记录的分期建议已调整，不把本节当作已发布施工规格或任务台账。

### 已完成基础：人物 Wiki 与作品、机构和研究笔记关联

这一步已形成 [人物 Wiki 施工规格](specs/作者档案与研究对象关联.md)：围绕个人身份汇集头像、介绍、作品、机构关系和多对象研究笔记，提供人工身份确认、合并及误并拆回。已确认规则维护于 PRODUCT，逐项答复保留于需求记录 R008。

它为后续研究评价与翻译提供持续可用的身份、关系及版本基础。七项流程已实现并完成整组独立验收与审查，导出和新目录恢复使用真实接口及文件验证；稳定编号与版本的继续读写证据见首版验收记录。实施与交付遵循 [Matt 工作流](agents/workflow.md)，未新增占位评分或翻译接口。

### 当前优先：借鉴 Zotero，完善基础数据库

围绕“收集 → 整理 → 查找 → 阅读 → 记录与引用 → 共享复用”核查实际缺口。借鉴功能服务的工作方式，在本平台内完成，不要求成员转用 Zotero。已有专题、笔记、去重、引用快照和权限历史继续复用；补齐与改善的范围须通过现状对照确定。

建议优先评估低成本录入与批量整理、资料与附件对应、清晰的列表及筛选、全文查找与阅读定位、笔记和出处复用。阅读桌、紧凑来源列表、暂存比较、专题交接等 UI 候选及其依据见 R011；这些尚未逐项确认，不等于全部列入首批。附件全文、OCR、引文格式等分别判断投入与实际需要，基础数据库的完成边界由后续规格确定。

截至 2026-10-26，[基础资料管理第一批](../work/基础资料管理第一批验收.md)已交付列表阅读、批量整理及本地附件文字检索；[链接与编号辅助录入](specs/链接与编号辅助录入.md)已通过 PR #33 交付单篇题录取得、人工核对与保存。不能据此宣称整个内化方向完成。

本轮[个人常用检索](specs/个人常用检索.md)、工作位置返回及候选完整性已集成并完成[本地验证](../work/常用检索与资料工作流验收.md)，最终交付分别由 [#34](https://github.com/normaltank/DataBase/issues/34)、[#30](https://github.com/normaltank/DataBase/issues/30)、[#31](https://github.com/normaltank/DataBase/issues/31)跟踪。标准题录交换按[规格 1.0](specs/标准题录交换.md)实施本轮 RIS 导入预览、人工核对保存、原始依据与选中导出闭环；集成、审查及交付状态见 [#36](https://github.com/normaltank/DataBase/issues/36)／[PR #53](https://github.com/normaltank/DataBase/pull/53)，其他交换格式未纳入。CSV、可读内容包与完整备份继续服务各自用途。结构化标签、OCR、引文格式及批量采集仍未实施，按真实工作需要分别确定范围。

### 随后：从来源采集文章

建设方向已经确认，具体方案待细化。建议从少量有代表性的期刊、机构、智库来源跑通“发现文章 → 保留来源与原始信息 → 识别重复 → 人工核对 → 入库 → 后续更新”。已有导入针对试点主表，不能当作已完成通用网站采集。

需要明确首批来源与时间范围、采集题录还是同时保存正文／附件、手动触发或定期更新，以及采集结果进入候选区还是共享库。技术上按来源评估官方接口、订阅源或网页解析；保留原始 URL、获取时间和失败原因，重复运行避免重复入库，来源变化与平台人工修订分别处理。这些是方案建议，不是用户已指定的技术实现。

采集的作用是补充可管理的研究资料。沿用既有身份、核对、权限和历史规则；各网站获取条件及可保存内容在接入时核查。来源覆盖、更新频率和维护工作量应可说明，不以“各种来源”承诺任意网站均可自动获取。

### 后续候选：形成可维护的研究档案与评价记录

在首版笔记研究对象关联的基础上，继续复用摘录、专题和报告，形成针对作者、期刊或机构的评价记录。建议每份评价说明研究问题、对象、时期、依据、研究员和版本，并区分材料登记的事实与研究员判断。

先围绕真实课题开展人工定性研究，同时分别积累学术影响和政策／社会影响证据。需要数字时，再明确指标含义、数据来源、覆盖范围、时间窗与比较对象；资料不足应显示不足，不能自动判为“影响力低”。

建议验收一条完整路径：选定对象和问题 → 整理材料 → 比较证据 → 分别形成两类影响评价 → 生成能返回依据的报告。作者、期刊和机构的评价可以使用不同指标，不能直接共用一套总分。

### 后续候选：接入有版本对应的翻译流程

下述为首批接入前的分期建议。单篇题名／摘要、机器版本、人工采用与失败重试已由 [PR #50](https://github.com/normaltank/DataBase/pull/50) 交付；正文／附件、批量及完整多语研究工作仍为后续候选。

先把“哪份原文的哪个版本，译成哪种语言，经过哪些修订”表达清楚。建议将原文、机器译文和人工校订记录分别保存，记录所用服务、模型、时间及相关处理设置；专名与术语积累可人工维护。

新增翻译不覆盖人工校订；原文变化时能识别译文需要复核。中文译文与原名参与检索，搜索结果说明匹配的是哪种内容。具体哪些字段、正文和附件先进入翻译流程，按实际使用选择。

2026-10-23 制订上述建议时未接入 API、未发送本地材料。2026-10-27 已交付的单篇适配及重试按已冻结范围实施，真实 API 仅用合成题名／摘要完成冒烟；后续扩展仍需明确材料与用量边界。

### 更长期：按真实问题增加分析工具

在作者身份、关系与证据质量足够时，再评估引文关系、合作关系、主题变化、跨对象比较和可视化等工具。是否需要外部学术数据、批量分析或专门的图形界面，依据研究问题和资料覆盖决定。

这些是候选实现方式。没有必要在业务模型尚未确定时先搭空的分析接口或复杂任务系统；每次增加能力都应有可验证的使用场景。

## 6. 对后续建设的具体约束

已确认方向及原有可追溯原则由 PRODUCT 约束后续建设；建议技术方案遵守以下衔接方式，具体实现仍可调整：

1. 原文作者身份与登录账号分开。已有个人成果 author_id 的权限含义保持明确，不复用成外部学者编号。
2. 作者、期刊和机构身份尽量复用同一份记录。增加关系与内容，避免为研究页面复制一套互不相认的对象。
3. 保留原始署名、名称、出处和版本。新结构通过增量迁移接续旧资料，不能以完成“结构化”为由丢弃未能识别的信息。
4. 事实、原文、译文、研究解释及指标计算结果分别保存各自依据。现实有效时间、资料发表时间、核查时间和修改时间分别表达。
5. 新对象、关系和译文同步纳入既有权限、历史、导出及恢复流程。可从页面找到一份内容，不等于取得改写它的权限。
6. 以真实可用的能力判断完成。稳定编号、有效关系、证据关联和可恢复的版本，比仅增加按钮或接口占位更重要。

这些要求可以在现有应用中逐步落实。技术方案随规模和实际研究任务调整，不先设定更换整个技术栈。

## 7. 后续什么时候需要再 Grill

长期影响力与多语使用的关键口径已经明确，本轮基础数据库优先、随后采集的方向也已确认。记录这些方向无需重复 Grill；形成当次施工规格时，先核查现有功能与来源样本，再围绕确实影响业务范围的问题确认：

- 后续基础资料管理批次的具体缺口与验收边界；已交付批次及个人常用检索沿用各自规格。
- 首批文章来源与时间范围、题录／正文／附件范围、触发与更新方式、采集结果如何核对入库。
- 首个真实研究问题、对象和时期，以及研究人员希望得到怎样的成果。
- 两类影响力分别需要哪些证据和比较方法；可用数据能支持哪些结论。
- 第一批翻译覆盖哪些内容、哪些可以发往外部服务，以及人工校订怎样进入日常工作。

这些问题不妨碍现在明确产品方向，也不应被默认指标、模型输出或现有字段替代。

- OpenAlex 将作者与作品分别建模，用作品署名关联记录原始姓名、署名位置与机构。本项目可借鉴这种区分，并保留人工核实和纠错。见 [作者模型](https://help.openalex.org/data/authors/) 与 [作品署名关系](https://help.openalex.org/data/authorships/)。
- DORA 建议不要用期刊指标代替对个人研究贡献的判断，并重视政策和实践等定性影响。我们据此建议保留评价依据和适用范围；两类影响分别评价是本项目用户确认的方向，不是从外部标准推导出的强制模板。见 [DORA 宣言](https://sfdora.org/read/)。
- DeepSeek 官方提供可通过 API 接入的服务，说明它可以作为未来翻译流程的候选提供方；能接 API 不等于已验证翻译质量或已具备版本管理。具体模型与费用在实施时再核查。见 [DeepSeek 官方 API 文档](https://api-docs.deepseek.com/)。
