## R001：来源目录分类、国别检索及详情字段

### 用户提出的问题

1. 进入来源目录后，无法按国家分类查找期刊，也无法筛出国际期刊。
2. 来源类别过多，不方便理解和管理。
3. 来源详情似乎使用统一卡片，机构也出现 ISSN 等不适用字段，并显示“待补充”。

### 改进前已核实的现状（历史基线）

- 来源页及来源列表接口均没有国别筛选。资料库中的“资料研究对象”筛选不能替代这一功能。
- 只读核查数据库：44 条期刊登记的国家字段全部为空。后续需要按下文已确认的口径补充有依据的信息，增加筛选控件本身不会补齐数据。
- 来源页显示六个类型入口：智库与政策研究、机构与大学、期刊、其他连续出版物、发现入口、来源表出版物。最后两类混入了采集入口与导入来源的信息。
- 来源详情及编辑表单使用统一字段集合，机构也显示主办机构、出版机构、ISSN 等字段。没有区分“不适用”和“信息尚缺”。
- 相关实现：`static/app.js` 的 `sourcesPage`、`openSource`、`sourceForm`；`platform_app/web.py` 的 `sources_list`；`platform_app/importer.py` 的连续出版物导入。
- 该次核查时，旧术语表已区分机构和期刊，期刊地域归属的判定规则尚未确认；后续确认结果见下文。

结论：统一管理来源是原型的实现取舍；把内部分类直接暴露为用户入口、对不同对象套用全部字段，以及遗漏国别浏览，是需要纠正的设计问题。不能把机构的 ISSN 留空解释为机构信息有待补齐。

### 已明确的改进方向

- 来源目录要便于按国家查找期刊，并支持用户需要的“国际期刊”检索。
- 用户可见的分类要简明、可管理。
- 对象不适用的字段不能显示为“待补充”。详情和编辑都应遵循对象含义。

### 本轮 Grill 结论（用户已确认）

2026-10-21，指挥 Agent 在文档派工期间转达用户选择结果：

1. 期刊按主办方国家归类，出版方国家另记。用户选择的推荐项包含：多国共同主办可归多个国家；依据不足标“待确认”。
2. 国际期刊按有依据的国际办刊定位标注，与国别并存；不因外文或某个外国出版社就自动判为国际。

以上口径先进入产品宪章和术语表；文档阶段没有增加筛选或修改数据。后续实现动态读取主办关系和机构国家，不把计算结果回填旧期刊 country 字段；数据依据层级和实际缺口见本节实施结果。

### 机构身份与关系（Grill 4 已确认）

此前用户指出，有些智库与大学或其他机构有关，可能是子机构，要求先讨论更合理的目录分层。当时“机构类型与机构间关系分开”等仍是提议，前次文档据此保留了未决状态。

2026-10-21，指挥 Agent 随后转达：以下完整提问获得用户选择“采用这个方案（推荐）”：

> 是否采用‘按类型浏览、用关系展示层次’的方案？有明确身份且持续提供资料的子机构独立登记，只登记一次；大学详情可查看下属机构，智库筛选也能找到它。共同设立可关联多个机构，合作/资助单独说明，期刊通过主办关系连接机构。

据此，机构身份与关系原则已迁入 PRODUCT，已明确词义进入 GLOSSARY。每项实际关系仍须有证据：联合设立不强制单一上级，合作或资助不自动视作隶属，也不从共同主办期刊反推机构隶属。

用户确认了按类型浏览及关系层次原则，未逐字确认前台标签的名称、数量或固定页签清单；这些留给后续实施方案。采集 Agent 另行核查真实机构关系样本，本次文档不等待样本完成，也不把尚未核实的实例写成已确认事实。

### 后续派工与实施结果（2026-10-21—22）

指挥方选定机构、期刊、其他出版物三个主要入口及全部入口；年鉴、工作论文系列归其他出版物，门户归维护区。这是可调整的实施方案，用户确认的长期原则仍为类型浏览与关系层次，未把三个标签固化为永久规则。旧出版物编号、资料关联与历史保留，不自动合并。

已实现期刊主办国别和国际定位的组合筛选，机构类型筛选、适用详情和编辑字段、机构关系双向浏览及维护。主办关系采用有依据的机构办刊归属或学术组织责任，不强制法律所有者审计；已有登记未在小样本复核中重验，不等于已证伪。原表明确待核或实际冲突时保持待确认。

独立验收补充了两项修正：类型不能因描述中出现大学而继承上级身份；对象类型不能永久锁死。默认分类与本轮自动标签均已纠正，历史高校的高校身份和历史状态分别保留，LV PEAK 的智库身份兼顾全新导入。已有来源可安全更正类型，机构关系或主办／出版引用有明确阻断提示；其他不适用字段保留在历史。

本轮通过 34 项自动测试、增量迁移与备份恢复比较、隔离浏览器写入及恢复、本机只读验证。指挥方使用研究员身份独立确认组合筛选、切换类型清除条件、PEAK 唯一身份、学院导航和无 ISSN 表单。完整修改清单、证据和截图见 [执行及验收记录](../work/来源目录改进执行记录.md)。

用户明确：“宪法，就是定义产品的文档，确保所有 agent 知道项目是干什么的。也可以对 agent 进行约束。”

据此，产品定义是宪章的主体，让所有 Agent 对项目目的、使用者、范围和核心业务有共同理解；必要约束可以包含其中。具体执行流程不能取代产品定义。已有用户共识应从原讨论中提炼保留，不重新当成未决事项。

### 组织建议（文档建设前的提议，保留出处）

产品宪章作为产品定义的权威出处；给 Agent 的入口文件引用它，并说明何时读取其他文档；施工说明记录当前怎样实现产品。建议宪章包含：

1. 项目使命、服务对象与长期目标。
2. 首期范围及长期方向，区分已确认功能与未来愿景。
3. 核心对象与关系：机构、期刊、原始资料、中心成果及其出处关系。
4. 共建、共享、核对、修订与权限原则。
5. 数据质量和使用原则，包括可追溯、可纠正、可导出，以及“不适用”和“未知”的区别。
6. 产品原则和必要边界，包括以研究员实际使用为依据、为后续研究与产出保留扩展空间。
7. 产品成功条件、仍需澄清的问题，以及怎样更新产品定义。

调研、派工、文件分工和施工验收的具体工作约定，可由 Agent 入口及相关执行文档承接。以上是当时的组织提议；本轮按后续文档派工采用了产品宪章、短 Agent 入口与现有文档分工，不将提纲中每一项建议自动视为已确认的交付细目。现有 Python、Flask、SQLite 等技术选择属于当前实现，不自动成为长期不可修改的项目原则。

## R004：成果作者与提交者的权限映射

**2026-10-22 确认、2026-10-23 完成本轮实现验收：** 用户在本轮开工后选择“采用这套作者授权规则（推荐）”：本人提交个人报告直接生效；代交时指定负责作者，由作者确认。正文仅作者及其授权同事修改；管理员负责核对、账号和备份，未经作者授权也不能改写或恢复个人正文。目录译稿仍全员共编。历史报告须显式确认负责身份，不能仅凭旧提交者/管理员权限自动推定。对应规则及权限验证已完成，见 [工作流程规格](specs/研究资料工作流程.md)。下段保留发现问题时的历史记录。

本轮文档核查发现：[现有权限实现](../platform_app/web.py) 按记录提交者、授权同事或管理员判断可编辑性，受限记录也按这些身份判断可见性。提交记录时的登录账号成为提交者，但原文作者与编译者是分别记录的身份。

### 向研究平台发展的建议顺序（提出时为讨论提议，随后获施工授权）

2026-10-22，用户再次询问一个可扩展为研究平台的数据库还需要什么。以下是指挥方结合现状的补充建议，不是用户批准的新功能清单。当前已具备来源关系、基本检索、收藏和专题、修订恢复、演示权限及备份；来源内容与目录译稿共编已确认但尚未施工。

1. **持续整理内容并复用同一份记录：** 先落实已确认的来源内容与独立译稿，明确网页正文、原文和附件各自的身份及版本。期刊页、专题和搜索引用同一份内容；从一个专题移除内容与删除内容本身分别处理。研究笔记等新类型的范围及权限仍按后续任务确定。
2. **资料身份与质量可维护：** 维护中文名、原名、别名及有依据的更名关系，识别疑似重复条目，由人核对合并并保留来源、旧编号及相关引用。现有按稳定编号跳过重复导入不等于已经具备通用的重复识别和安全合并。已知国别、国际定位等缺口继续按依据补齐。
3. **检索覆盖实际使用的内容：** 优先将新增译稿／笔记正文纳入检索，展示命中片段，并沿用来源、年份、类型等筛选。后续按实际材料需求纳入 Word、可提取文字的 PDF 及扫描件文字识别；别名和中文／原文名称帮助检索，但不把它们宣传为任意语言间的语义检索。
4. **摘录、判断与原文能相互追溯：** 在现有成果与原文关联之上，逐步支持摘录对应的页码或段落、原目录出处及引用时使用的内容版本。原作者观点、研究员自己的解释和译文分别标识，报告中使用的证据能返回查阅，而不是只能打开整份文件重新寻找。
5. **共建责任与实际工作衔接：** 目录译稿全员共编，个人报告沿用作者授权规则；落实保存冲突保留输入、修订和误改恢复，并对齐作者、译者、代上传者及管理员的权限。真实成员管理在多人试点前补齐。定期检查来源更新、缺失信息和待核内容，指定实际维护责任；自动采集若引入，应复用候选、去重及核对流程。
6. **资料长期可保存、可交接：** 现有备份、恢复和清单导出要覆盖新增正文、附件、关系及版本；正式使用时补备份排程、独立存放与恢复演练。按真实工作需要提供通用文献交换或与现用文献工具的衔接，不能把只导出标题清单视为完整迁移能力。
7. **专题服务具体研究问题：** 在现有专题收集之上，逐步记录研究问题、证据摘录、不同来源的观点比较、研究员判断及产出报告。先选择一条真实流程验证：译一期目录 → 选文阅读 → 摘录／笔记 → 专题比较 → 形成报告 → 从引用返回原文。具体分析功能不在本轮冻结。

建议优先顺序：先落实已确认的内容与共编能力，并衔接正文检索；随后完善别名、重复处理和带出处的摘录；正式多人试点前补齐真实账号、职责和运行保障；再围绕真实研究问题扩展专题分析和写作。录入时先填写必要信息、其他字段按需补充，并提供贴合材料类型的编辑方式，降低日常贡献负担。

建议采用任务验收而非只统计页面数量：新内容可独立搜索、多入口访问同一记录、同事修订不丢稿、引用可追溯，完整备份恢复后正文／文件／关系仍可用。以上仅用于讨论下一阶段的检查方向，尚未代替具体施工规格。

## R011：产品脑暴与基础数据库、来源采集的建设顺序

日期：2026-10-24。状态：五 Agent 脑暴已完成，用户要求记录，并明确当前建设优先级；功能细目尚未形成施工规格。本条记录讨论历史，生效方向维护于 [PRODUCT 第 6 节](../PRODUCT.md#6-长期方向)，当前建议路径见 [长期愿景第 5 节](长期研究愿景与演进路线.md#5-当前建设顺序与后续建议)。

### 用户原意与最新取舍

用户要求：“brain storm一下，想一想现有产品作为一个数据库，研究中心定位的产品还缺什么，调动五个subagent做这个讨论”。指挥方采用 `wide-open-brainstorm`，五位任务子 Agent 均显式设置 `gpt-6.1-sol / high`，受并发限制分批参与；角色分别为研究员工作流、资料质量、研究分析、中心协作及 UI 体验。研究员与分析角色随后互相质疑优先级和结构化负担。

据此确认先完善基础数据库、再推进来源文章采集。不能直接使用 Zotero 的具体原因未展开，不自行推断；此前建议将通用功能交给 Zotero 的路线不再作为本项目默认方案。应借鉴适用功能，在本平台内完成基础流程，不能把直接使用 Zotero 作为前提。是否复用其代码、具体借鉴范围及功能完整度尚未决定。长期定性研究、双维度影响力和保留原文的中文使用方向继续有效；用户没有逐项批准全部脑暴建议。

### 脑暴依据与限制

本轮只读核对当前主分支的产品文档、实现及此前 UI 证据。人物 Wiki、资料共编、历史与权限、专题、摘录、固定引用、可读导出及完整恢复已有实现，不能再次列为缺失。附件全文提取／OCR、通用网站采集、完整原译版本流程和专门影响力评价尚未提供，现状依据见 [施工说明](施工说明.md)。

体验角色核查到来源目录仍为三列卡片、长题名空间有限；专题与资料使用同一抽屉，打开资料会替换专题内容；工作台以草稿和近期内容提供续作入口。这些是实现观察，不证明研究员必然因此迷失或效率下降。持续真实研究员试用尚未开展，脑暴建议不能作为使用效果的验收证据。

### 保留的七组候选方向

1. **研究工作界面。** 阅读时保留问题、材料和笔记上下文；来源增加适合长题名的紧凑列表与译目入口；人物按时期联看任职、作品和研究笔记。沿用蓝、白、柔黄及少小字的已确认风格，改善阅读和比较动作。
2. **收集与取得原文。** 降低首次登记成本，支持后续补齐与批量整理；区分出处线索、外部文件和已保存附件。评估附件文字提取、带位置的检索命中、可解释匹配与跨语词汇对应；从实际样本判断 OCR 和自动化范围。
3. **比较与可核查判断。** 围绕具体问题和时期比较对象，连接判断与具体证据，允许保留反例、其他解释和资料不足。已有专题、摘录及固定引用先行承载，分类和表格按实际课题细化。
4. **研究范围与空缺。** 区分未收录、未查过、查过但未找到。先在专题自由文本留下“为什么选这些材料、还缺什么、下一步做什么”，不预设完整覆盖账本为必填项。
5. **影响力个案。** 分别积累学术讨论和政策／社会作用的具体事件、时间、出处与解释；提及、批评、赞同、采用分别理解，不能从引用或时间先后直接推断因果影响。先有可核查个案，再细化指标。
6. **原译对照阅读。** 用少量核心材料验证原文定位、中文阅读、机器与人工标识、专名术语及版本对应。原文变化后识别待复核译文，保留人工校订和旧引用依据；不以全库批量翻译作为唯一起点。
7. **研究交接与持续维护。** 专题呈现问题、当前判断、关键依据、分歧与下一步，让同事接续；贡献者保留署名及责任。明确重点来源维护人、替补和运行安排，不把贡献量变成人员排名。

### 分歧、验证建议与长期构想

资料角色优先收集成本、全文与检索；分析角色优先覆盖边界、研究判断和有条件的比较；体验角色优先双页阅读、来源列表与交接编排。工作流角色指出，完整账本、判断卡或独立工作桌都可能增加维护负担。第二轮收窄为：判断应能回到当时的具体依据并保留责任与版本；其余先用自由文本，只有反复发生的困难才增加结构。

建议用两名研究员、一个真实问题、六份材料开展小实验，包含一份相反材料和一份难取得的全文。第一人形成有出处的短判断并留下上述三句话，第二人隔两天独立接续；观察主要阻塞来自取得全文、理解、比较还是交接。可用现有专题和离线 UI 原型进行，不要求先开发新系统。此实验尚未执行，也不是用户已承诺组织的试用。

最强反对意见是：若平台要求重复登记，却没有持续跨人复用，录入与维护成本可能超过收益。当前既无证据否定项目，也无证据支持无限扩张；应比较真实工作的净收益。该质疑不等于要求用户改用 Zotero，也不改变其最新建设顺序。

保留的长期构想是“可接续的研究判断”：新成员能理解前人为何判断、当时看过什么、仍缺什么；新材料出现后提示哪些判断可能需要重审，由研究员决定修订。讨论中的六／十二／二十四个月仅用于想象成熟过程，未作为排期承诺。复杂关系大图、综合排名、自动结论和全库翻译不自动进入近期任务。

### 来源采集的已确认方向与待细化事项

## R021：自采集、自维护与前端重设计

日期：2026-10-27。状态：十四项业务答复及整体方向已确认，进入施工规格与任务图整理；应用尚未施工。用户认为当前前端臃肿，明确要求通过该技能澄清大改方向；随后指出要去掉重复、冗余和无价值功能，数据库重要但人不愿填写的信息应尽量交给 AI／后台完成。用户明确理想体验是“偶尔上线看一眼对象国有哪些新文章”，最终目标为“自采集自维护的数据库系统”，包括从机构、期刊等来源采集文章、DeepSeek 翻译、关联条目及整理作者。不能只关注其举例的时间筛选，还应通过多个子 Agent 主动核查完整流程。

### 已确认答复

1. **机器结果展示：** 对“采集、去重和机器翻译完成后直接进入新文章列表，标明机器处理和未人工核对，只把失败、冲突和可疑条目交维护者”的问题，用户选择“自动展示，异常再人工处理”。正常文章展示不以逐篇人工批准为前提，仍不冒充人工已核对。
2. **身份关联：** 建设方明确说明此项会放宽旧的全部人工确认要求，提出 ORCID、机构个人主页等明确依据可自动建立作者与作品关联，仅同名不合并，证据不足保留候选；用户选择“有明确依据自动关联，存疑留候选”。具体自动证据标准、冲突及纠正方式留待规格细化。
3. **自动翻译范围：** 用户选择“题名与摘要自动翻译，全文按需”。只翻译实际取得的原文摘要，缺摘要明确显示；公开正文取得与按需全文翻译不是已经交付的功能。
4. **对象国与来源：** 对拉脱维亚机构发表研究乌克兰的文章这一场景，用户选择“首页看研究该国的文章，另可看来源全部更新”。首页按文章实际研究对象组织，来源所在地保持独立。
5. **收录内容：** 用户选择“研究内容优先，排除一般事务通知”：默认收论文、研究报告、政策分析、评论及有研究价值的新闻分析，排除活动预告、招聘和一般机构通知；特殊来源可以单独调整。
6. **新增口径：** 用户选择“新增按首次收录，另可筛发表日期”。上次访问后首次收录的文章优先，旧文修订及译文变动另作更新；补收旧文仍进入新增，发表日期独立筛选。
7. **数据库与写作的分工：** 建设方曾建议保留次级“研究工作区”，用户进一步收窄：“站内的个人编译写作确实是没必要的，现在有编辑，导入，导出的功能就够了。一般来讲，数据库的功能就是存储源数据，存储写好的报告。”据此去掉专门的个人编译写作流程，保留资料与成品成果的保存、编辑、导入和导出；不把建设方的“研究工作区”建议当作已获同意。专题、笔记与证据组织的具体界面边界仍需按此分工澄清，不由技术默认值补作决定。
8. **阅读密度：** 用户没有采用每条默认显示短摘要的建议，而选择“题名列表优先，一屏放更多文章”。新文章默认紧凑题名列表，摘要在进入条目后阅读。
9. **翻译失败的读者体验：** 用户选择“先显示原文，中文稍后自动补齐”。翻译暂不可用或额度不足时，原文题名和已有信息仍可见，标注中文待处理；恢复后自动续作，不要求普通读者逐条重试。
10. **资料夹边界：** 用户明确“Q10、Q11、Q12 都按你的建议来”，确认保留简单资料夹和备注。文章与成品报告可收集到资料夹，移除填写研究问题、比较判断、组织摘录及撰写报告等专门工作流，已有内容和历史仍可查。
11. **采集范围治理：** 用户确认管理员确定采集来源。成员仍可提交来源，AI 可以推荐新来源，管理员确认后才启用；启用范围内由系统负责持续取得与更新，不要求普通读者逐篇操作。
12. **费用控制：** 用户确认 AI 调用设置月度费用上限。超限暂停 AI 处理、继续采集与展示原文，额度恢复后续作；具体金额在小批试运行了解消耗后设置。用户要求继续把整体方案梳理清楚。
13. **原文保存：** 建设方展示整体草案并建议保存实际取得的公开网页正文快照和出处、PDF 等文件按需保存；用户答复“按你的建议来”。原文快照与题录、外链分别表达。
14. **机器概述：** 同次答复确认：没有原始摘要时，可根据实际取得的正文生成单独标识的机器概述，原文摘要仍留缺；取不到正文就保留题名及已有信息，不生成无依据概述。

### 后续答复：本机选题报告、平台外选文与中心产出优先

建设方在Q2建议从资料库选择文章、补推荐理由提交，默认不用另写Word选题报告。用户明确否定：研究员先从本人负责的国家出发，优先找本国期刊、智库等信源的文章，按主题挑几篇，在自己电脑上按固定格式写好再交负责人。用户要求先把采集覆盖和检索做好；不能将研究员限制于平台内已有文章。据此确认本机固定格式选题报告与开放选文入口，不将平台逐篇选择或先完成题录入库作为交接前提。当时尚未提供模板，后续读取见下节。

用户对Q3的可见范围问题表示不理解，转而明确全过程留档：每一期选题应从流程开始保存。例如以“东欧的少数民族问题”为本期主题，在平台开启选题，对应研究员和负责人开展工作，工作成果在数据库留档。用户强调：“数据库要储存的其实是中心自己的产出，其次才是外部信源的产出。”据此将中心产出优先及一期选题的过程材料和最终成果留档作为产品方向；保存起点不等于共享起点，不能把此答复解释成已经同意此前建议的稿件可见范围。

用户对Q4表示“我已经提过了”。沿用其已经说明的流程：各国研究员挑选几篇候选，选题会上决定各国采用的文章。不重复追问数量，也不将建设方建议的多篇、候补、暂缺或固定一国一篇擅自写为业务限制。

本轮校正此前“仅看新文章、保存成品”的理解：基础设施服务中心工作；站外写作与全过程保存并行。该更新进入PRODUCT和术语表，R021原答复及固定规格保留历史身份；新协作方案仍在讨论，应用、任务派工与真实库保持未施工。接续优先了解现用选题报告模板及实际交接材料，再用具体场景澄清访问范围和任务组织。

### 模板提供与保存范围确认

用户提供ThinkTank中指定的《编译选题模板.docx》，同时问：“但是真的需要这个吗？这些应该研究员自己在个人的设备上写吧。”并表示：“其他的你说得对。尤其是对于平台应保存的部分，我赞同。”据此重申本机写作与文件交接边界，确认前一轮列明的保存范围：本期主题和参与者、候选选题报告、选题会决定及采用文章与分工、编译和审稿各版本、最终成果及与本期和原文的关联。

建设方仅只读查看用户指定的单个DOCX正文结构，未修改原件、读取整个ThinkTank目录、访问样例链接或导入示例数据。模板包含期刊选题与智库选题两类示例，主要栏目为题名、内容摘要、关键词、作者信息、来源，示例还涉及编译员署名。这里只记录材料结构，不复制示例正文或内部人员信息；模板并非一套要求研究员在平台重新填写的字段。

模板用于理解收件和留档对象，平台接收已写好的文件并保存版本。额外的正文索引、候选识别或题录关联不作为上传和交接的前置要求，不能据本次提供模板推定已授权站内写作、模板生成或将内部稿件发送第三方。用户对保存范围的确认不自动决定未定稿材料的可见范围；后续以具体使用场景澄清。整体仍处业务讨论阶段。

### 期刊编译与主题编译分别组织

建设方在Q9建议期刊概览围绕期刊和卷期或覆盖范围单独组织，复用本机编写、文件提交、审稿和归档，不强制经过主题选文会。用户明确：“期刊是期刊，主题编译是主题编译，这两者要分开。但是期刊也可以按同样的模式来保存留档。”据此确认两条独立业务，共用文件和版本保存能力，不将期刊编译挂在某期主题选题之下，不强制套用主题编译的候选或会议步骤。

主题编译按中心本期主题和各国选文组织；期刊编译按期刊、原刊卷期或覆盖范围组织，具体期刊档案和目次设计继续沿用R020及原规格，不因共用留档就把全部期刊字段、年度指标或成品生成并入本次平台讨论。两条业务分别保留过程材料和成果，适用的既有可见范围与编辑授权继续保留。规则和词义同步进入PRODUCT与GLOSSARY，应用仍未施工。
