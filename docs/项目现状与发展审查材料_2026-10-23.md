## 1. 项目要做什么，目前到了哪里

我们是乙方建设方，研究中心是使用方与甲方。项目暂用名为“知汇 · 研究资料共建平台”，面向研究员及承担资料核对、管理工作的人员。

希望解决的核心问题是：机构和期刊线索、单篇资料、目录翻译、个人笔记及研究报告分散保存，难以查找、共同维护和复用，也难以从成果追溯其依据。研究员既是资料使用者，也是内容贡献者。

产品的近期目标是建立可持续维护的研究资料库；长期目标是在这些资料之上支持专题研究、比较分析与成果产出。拉脱维亚是首批试点范围，不是平台永久限定的地域。

截至本文日期，已经完成四部分工作：

1. **本地基础平台：** 登录、来源和资料管理、成果提交、原文关联、核对、历史恢复、收藏、专题、导出及备份。
2. **来源目录改进：** 对象分类、期刊国别与国际定位、机构关系、按对象显示适用字段。
3. **前端整理：** 蓝、白、柔和黄的学术风格，删减口号和重复小字，改善详情及表格阅读。
4. **研究资料工作流程：** 来源介绍与独立目录译稿、网页正文、共编冲突处理、别名与人工重复整理、研究摘录、专题研究问题与比较笔记、报告固定引用依据、本机成员管理、可读内容导出和完整恢复。

当前有真实导入的试点元数据，本轮新增研究流程主要用隔离样本验证。**功能已经做通，尚未形成研究中心真实成员长期使用后的效果证据。** 本地完成也不代表已经具备正式联网运行、服务承诺或甲方合同验收条件。

## 2. 产品边界与使用原则

### 2.1 近期范围

优先把来源、资料、译稿和研究成果管理清楚，使成员能够查找、贡献、修订、引用、导出，并在误改或故障后找回数据。技术方案可以调整，但不应因此丢弃既有编号、关系、历史和人工积累。

用户希望界面美观、实用、学术，操作与说明尽量直接。当前颜色参考北外校徽的蓝、白、黄进行应用设计，不宣称复刻官方视觉规范。机构不适用的 ISSN 不再显示成“待补充”；缺失信息、未知结论与不适用字段需要区别表达。

### 2.2 尚未纳入当前交付的能力

尚未提供自动采集和增量更新、附件全文提取与 OCR、实时同步协同编辑、自动翻译与自动分析、语义检索、独立政策事件库或统计事实库、对外公开网站，以及正式多人联网部署。

可以上传 Word／PDF，不等于可以在线编辑这些文件；可以保存原文链接和引用时信息，不等于已经保存整篇外部网页或 PDF。长期研究分析功能尚未冻结。

### 2.3 不应在后续扩展中破坏的原则

- 有依据的信息才写成事实，未知内容保留未知，不为填满字段而猜测。
- 同一对象和同一份内容保持同一身份，多个入口只形成关联，不重复建档。
- 共同维护公共积累，同时尊重个人成果的作者责任与编辑授权。
- 研究判断与其依据分开保存，修订不能悄然改变旧成果采用的证据。
- 核对表示登记信息的检查进度，不表示平台认可材料观点或研究结论。

## 3. 业务对象及已确认的关系规则

| 对象 | 在项目中的含义 | 与其他对象的关系 |
| --- | --- | --- |
| 机构 | 智库、大学、学院、研究所等有明确身份的组织 | 可以隶属于其他机构、由多方共同设立，也可以合作或接受资助；可以主办期刊、发布资料 |
| 期刊 | 持续出版、可按刊名和卷期识别的刊物 | 主办机构与出版机构分别记录；期刊与其中的单篇文章分别登记 |
| 其他出版物 | 年鉴、工作论文系列等来源对象 | 可以关联机构，并承载单篇资料、介绍或译稿 |
| 单篇原始资料 | 文章、报告等被收录和使用的资料 | 关联发布机构、所属出版物和原文入口，可被多份成果引用 |
| 目录译稿 | 一期、多期或某个覆盖范围的目录翻译 | 每份独立保存；在相关来源详情汇总，也可从资料库、检索及专题访问 |
| 研究摘录／笔记 | 原文片段、译文、研究员解释及定位信息 | 指向所据原文和版本；当前实现复用研究笔记类型 |
| 个人编译成果／研究报告 | 有明确负责作者的中心成员成果 | 可关联多篇原始资料和研究摘录，保留采用时的引用内容 |
| 研究专题 | 围绕研究问题组织资料与阶段研究 | 收集原文、译稿、摘录和报告，保存比较笔记与阶段判断；移出专题不删除内容 |
| 发现／采集入口 | 帮助发现资料的网站或门户 | 当前放在维护区，不混作期刊或研究机构 |

### 3.1 机构层次：按类型浏览，用关系表达层次

用户已经确认：有明确身份、持续提供资料的子机构可以独立登记，但只登记一次。例如，某大学的一个智库既能从大学详情找到，也能从智库筛选找到，两处指向同一记录。

共同设立允许关联多个机构，不强制选择唯一上级。隶属、共同设立、合作、资助分别表达并保留依据。共同主办期刊不能被当作机构之间存在隶属关系的证据。

当前前台主要分为机构、期刊、其他出版物，机构内再按类型筛选。这是本轮采用的界面方案，未来可以优化入口，不能因此改变上述身份与关系含义。

### 3.2 期刊国别与“国际期刊”

用户已经确认：

- **按主办方国家归类期刊，出版方国家另记。** 多国共同主办可归入多个国家；缺失或角色有疑问时保留待确认。
- **国际属性按有依据的国际办刊定位标注，与国别并存。** 当前为“是／否／未知”，不能仅凭使用外语、刊名或外国出版社判定。
- 机构所在地、来源研究覆盖范围、单篇资料研究对象是三个独立维度。拉脱维亚机构发布的资料不自动被标为研究拉脱维亚。

例如，拉脱维亚机构主办、英国出版社出版的期刊，国别仍按其主办方登记；是否具有国际办刊定位需要另外的依据。

### 3.3 来源关联与原文引用

“这份内容与某个来源有关”“由某机构发布”“刊载于某期刊”“引用了某篇原文”是不同关系。当前使用一般来源关联连接介绍或译稿，不把它自动改写成发布机构或原文引用。

成果与原始资料是多对多关系。原文尚未入库时，允许先记链接或出处，再人工补齐关系。原文作者、译者／署名、负责作者账号、上传者、最后修改人分别理解，不互相替代。

## 5. 共建、作者责任与权限

这部分包含用户明确作出的业务决定，也包含当前本地实现的可调整安排。审查时应分别看待。

### 5.1 已确认的编辑规则

| 内容或操作 | 已确认规则 |
| --- | --- |
| 公共来源信息、来源介绍 | 成员共同维护 |
| 目录译稿 | 默认全体有效成员共同编辑，保留修改人与版本 |
| 本人提交个人报告 | 本人作为负责作者，直接确认生效 |
| 替他人提交个人报告 | 指定负责作者，由该作者确认；上传者不会因此获得作者身份 |
| 个人编译成果、研究笔记、研究报告正文 | 由已确认的负责作者及其授权同事修改或恢复 |
| 管理员操作个人正文 | 管理员身份本身不赋予改写或恢复权限，仍需作者授权 |
| 历史个人成果 | 需要显式认领或指定作者确认，不能按旧上传者默认认定 |

普通内容提交后在允许的范围内共享，先标待核对；指定人员检查后标记已核对。当前核对工作由管理员执行，正式人员分工仍需确定。

### 5.2 当前读取与运维安排

当前受限内容按提交者、负责作者、有效授权及管理员的读取范围控制；个人收藏和个人专题只向本人展示，中心专题可共同维护。正文、附件、检索和内容导出执行读取权限检查。

**管理员不能默认修改个人正文，不代表管理员不能读取受限资料或取得完整备份。** 完整备份包含全部账号的资料、历史和账号数据，属于运维保管范围；普通内容导出则仅包含当前用户有权读取的内容。这两种用途不能混淆。

目前尚未形成覆盖全部正式使用情形的保密分级、对外分享、成员离职及内容移交规则。已导出的离线文件也不会随在线权限变化自动收回，这需要后续使用制度明确。

## 6. 一条已经实现的研究工作流程

以下是功能示例，不是本项目已经完成的真实研究成果：

1. 研究员找到某拉脱维亚期刊，在其详情下保存“2026 年第 1 期目录译稿”，填写目录出处、网页表格并附上已有文件。
2. 同事继续修订该译稿。如果两个人从同一旧版本开始编辑，后保存者收到冲突提示，原输入保留，明确对照处理后再保存。
3. 研究员从目录发现一篇文章，登记原始资料；阅读后保存某一段原文、译文、自己的解释和页码。
4. 将原文与摘录加入围绕具体问题的专题，逐步写比较笔记和阶段判断。
5. 撰写个人报告，选择所用摘录。报告保留采用时的摘录内容及其所据原文信息。
6. 后来摘录或原文登记发生修改，旧报告的依据保持原样；成员明确刷新引用才采用新版本。
7. 在当前读取权限允许的范围内，从报告返回摘录及原文，或者导出可离线阅读的内容包。

这里有两个容易高估的地方：

- **引用版本固定不等于原文全文永久保存。** 新原文快照包括编号、类型、题名、原题名、作者、日期、链接、DOI 和版本等登记信息；实际引用片段单独保存。只有已保存的正文或附件才有相应内容，外部链接本身仍可能失效。
- **保存旧证据不绕过当前权限。** 当前无权读取相关笔记或原文时，对应摘录及引用片段会隐藏。如何兼顾长期可复核性与后续权限变更，仍值得在正式试点制度中审查。

### 7.2 导入与使用边界

初始输入为 ThinkTank 试点资料库的四张主表，只读导入本平台，保留稳定编号、原字段、导入报告和文件校验摘要。未读取个人稿件目录，也未将整个外部工作目录当作可共享资料。

原库的核验信息被保留，但平台的中心核对状态从待核对开始。已有附件主要保留官方链接与登记线索；没有批量复制并开放。新上传文件需由上传者确认可在所选范围共享。

再次启动不会重复导入或覆盖平台内人工修订。自动同步上游新增、变更和删除尚未实现。本轮扩展未向真实库添加测试译稿或研究报告，写入验证主要在隔离数据目录完成。

## 8. 技术实现与维护现状

本节用于帮助审查者判断现有方案与下一阶段是否相称，不把当前技术选型定义为永久约束。

| 层次 | 当前实现 |
| --- | --- |
| 后端 | Python；当前在 Python 3.12 验证，Flask 3.1.1、Werkzeug 3.1.3 |
| 数据存储 | SQLite，当前结构版本 5；保存来源、资料、成员、关系、专题和历史 |
| 附件 | 本地文件目录；数据库记录附件元数据与对应关系，备份恢复检查文件散列 |
| 前端 | 原生 JavaScript／CSS，无前端编译步骤，无外部 CDN 依赖 |
| 启动方式 | 本机启动和停止脚本，默认监听 127.0.0.1:8848；外部审查者不能通过该地址访问用户机器 |
| 数据升级 | 增量迁移；有数据时升级阶段先备份；恢复工具兼容结构版本 1—5 |
| 内容实现 | 多种资料和成果复用记录模型，另用关系表达来源关联、原文引用及证据采用快照 |
| 检索实现 | 对已登记字段及净化正文的派生文本进行匹配，尚无独立全文检索或向量检索服务 |
| 并发编辑 | 版本检查、冲突提示和浏览器本地草稿，不采用实时协同编辑系统 |
| 基础防护 | 登录和会话校验、请求防伪造校验、接口与附件权限检查、网页正文允许列表净化、链接校验 |

目前是集中在一台机器上的本地应用。尚未取得大规模数据、多用户并发、长期运行、故障接管或跨设备协作的性能与可靠性证据。现有基础防护和功能测试也不等同于独立安全审计。

源码按来源目录、研究工作流程、证据引用、重复整理、专题与成员管理等职责组织，但仍需结合实际代码审查模块边界与复杂度。不能仅根据本说明断言需要重写或已经足够扩展。

当前工作目录尚未纳入 Git。数据备份、数据修订历史和施工记录已经存在，但不等于有完整的源码版本管理、发布标记与代码回滚机制。正式继续建设前，工程交接方式值得一并评估。

## 9. 已做的验证，以及这些验证不能证明什么

### 9.1 已留存证据

- **后端行为与权限：** 一次 45 项全套测试通过；随后新增的恢复、旧证据权限和合并历史归一 3 项分别通过。这里不将分次执行描述为一次 48 项全套测试。
- **指挥方独立接口检查：** 来源内容阶段 20 项、研究流程阶段 13 项通过，另检查合并后恢复历史引用、完整备份恢复及真实数据保全。
- **独立页面流程：** 目录译稿、正文表格、刷新恢复草稿、两账号保存冲突与版本历史，以及原文→摘录→专题→报告→返回依据等流程通过。
- **引用版本检查：** 在隔离样本中把原文题名、作者和日期从 v1 改到 v2，旧摘录和报告仍展示采用的 v1 信息，没有用当前值补写旧依据。
- **数据保全与恢复：** 升级前后旧编号、既有字段和附件散列核对通过；恢复到新目录后业务表与文件核对通过，数据库完整性及外键检查通过。
- **离线导出：** 建设方检查 6 类页面在桌面与 390 px 宽度下共 12 种情况，23 个本地链接有效，表格、长链接和引用快照保持可读，内容导出不包含账号凭据。
- **正式本机只读检查：** 44 条期刊可浏览；“拉脱维亚＋有依据的国际定位”组合返回 2 刊；来源介绍、译稿入口与资料列表呈现正常，主题与适用字段保持。

附件草稿持久化和部分窄屏场景采用前端建设方的自测证据；离线阅读采用后端建设方的自测证据，未冒充指挥方独立检查。历史测试记录中的暂停、待收口状态已由后续完成记录承接，不能脱离时间顺序判断当前状态。

### 9.2 仍缺少的验证

目前没有真实研究员连续使用后的任务完成率、寻找资料耗时、录入成本、错误率或满意度数据；没有覆盖全部来源的事实审计；没有正式并发容量和大数据规模测试，也没有全面浏览器／设备矩阵或独立渗透测试。

因此，当前可以支持的结论是：**列明范围内的本地功能、权限和数据保全检查通过；研究价值、长期可用性与正式运行条件仍需试点检验。** 测试数量不应成为这些缺口的替代指标。

## 10. 未来愿景与候选发展顺序

长期希望形成三层能力：可靠积累资料；把资料转化为可追溯的研究笔记和成果；在具体研究需要明确后，再增加辅助分析工具。各层都继续使用既有记录和关系，不要求重建一个互不相通的新系统。

下面是目前指挥方提出、待外部审查和用户进一步取舍的候选安排。**它们不是新的施工授权、时间承诺或确定预算，也不是把尚未实施的能力列为现状。**

| 候选阶段 | 主要工作与目的 | 建议用什么结果判断是否有价值 |
| --- | --- | --- |
| A. 真实研究试用与数据核实 | 选择 2—3 个期刊和一个真实研究问题，实际录入译目、摘录并形成短报告；同步核实重点国别、国际定位、机构匹配及重复关系 | 研究员能用自己的材料完成全过程；记录卡住的位置、耗时和误解；每项事实修订有依据，未解决项继续标注 |
| B. 高频写作与交付体验 | 根据试用反馈改善 Word 表格粘贴和目录录入；考虑可编辑 Word 导出，带署名、卷期、出处及引用清单 | 用真实目录和报告验证往返编辑、表格保留、引用一致性及交付可用性；不只检查“文件能打开” |
| C. 附件可检索与资料互通 | 先讨论文字型 PDF／DOCX 的提取检索，再按需求考虑 OCR、文献管理工具及标准格式互通 | 能区分题录、网页正文与附件命中；显示提取状态和失败原因；检索结果能回到对应文件位置，权限一致 |
| D. 正式小范围多人试点 | 确认真实成员、运行位置、访问方式、核对责任、账号交接、备份保管和恢复演练；补齐源码版本与发布管理 | 在实际使用环境完成多账号流程与恢复演练，有明确维护人和问题处理方式，容量目标来自预计使用量 |
| E. 有明确用例的研究扩展 | 按真实议题评估更新线索收集、主题跟踪、比较研究工具，以及是否需要事件／事实数据结构 | 每项扩展能说清输入、输出、适用范围、人工核查与成效指标；保留原始依据，不把推测自动写成研究事实 |

这些阶段不是机械串行：若多人试用必须联网，阶段 D 的必要准备应前移；若附件检索已是试点的主要障碍，阶段 C 也可能先于 Word 导出。请审查者挑战排序，并说明依据。

当前倾向先做真实试用和数据核实，再决定新增功能优先级。理由是已有功能较多，而真实使用证据较少。这是建设方判断，不是已被用户研究验证的结论。

## 11. 正式推进前仍需明确的事项

1. **实际用户与规模：** 谁会持续贡献、谁主要阅读、谁核对；预计人数、同时在线人数、资料与附件增长量是多少。
2. **优先研究任务：** 第一轮要支持什么研究问题、目录翻译频率和报告形式；怎样判断比现有文件夹及个人工具更有效。
3. **内容范围与责任：** 哪些资料可内部分享、哪些受限；原始附件的授权、成员离职、成果移交、对外导出如何处理。
4. **运行与维护：** 由谁提供机器和网络，是否需要外出访问；谁负责升级、备份、恢复和故障处理；可接受的数据损失及恢复时间是多少。
5. **数据质量职责：** 哪些字段必须人工核查，谁维护来源变化，多久复查一次；如何区分历史事实、当前状态和来源自身的宣传性表述。
6. **正式交付标准：** 试点批次、验收人、优先级、预算与维护边界。当前没有据此作出确定工期或费用承诺。

这些问题不需要全部解决后才能做小规模本地试用，但与权限、共享和部署有关的决定不能由技术默认值代替。

## 12. 文档与 Agent 协作方式

项目由指挥 Agent 负责理解需求、与用户澄清、记录决定和派工；建设与前端等执行对话按明确范围施工。用户已要求以项目文档承接上下文，避免任务依赖某个模型或对话的记忆。

目前的文档分工是：

| 文档 | 权威职责 |
| --- | --- |
| `PRODUCT.md` | 产品目标、范围、核心对象关系和已确认的共建规则 |
| `AGENTS.md` | Agent 入口、按任务读取哪些文件、协作边界和完成条件 |
| `GLOSSARY.md` | 已确认的业务词义，避免多处重复定义 |
| `docs/需求讨论记录.md` | 决定出处、建议、用户答复与未决问题 |
| `docs/specs/` | 某轮已确认改动的行为、范围及验收条件 |
| `docs/施工说明.md`、`README.md` | 当前实现、操作、启动、备份与恢复 |
| `work/`、任务计划 | 本轮执行情况、检查证据及接续说明 |

文档体系参考过 Matt Pocock 的技能实践及其他一手工程资料，但没有把某一套模板或技能名称当作产品正确性的证明。重要取舍按需要记录，不为“完整”创建重复的空文档。

后续给执行对话的任务需要写清：工作位置、必读材料、当前完成状态、本次目标、文件归属、范围外事项和验收标准。多个 Agent 共用工作目录时需避免同时覆盖同一文件。用户变更模型后也应按这些材料恢复上下文，不假设模型一定失忆或一定记得。

本次仅整理审查材料，没有发起新一轮功能施工。审查意见应先区分事实纠错、范围内改进和新的业务决定，再由用户与指挥方决定如何落实。

## 13. 请审查者重点回答的问题

请把本项目视为一个真实但早期的内部研究工具，结合上述规模、团队和已确认规则审查。希望得到可以改变下一步行动的判断，而不只是通用功能清单。

### 13.1 产品与使用流程

- 当前从资料管理扩展到研究工作流程的方向是否连贯？有哪些核心场景缺失，哪些已经做得过多？
- 来源、资料库、编译成果、专题等入口是否可能让研究员难以判断“应该把东西放在哪里”？怎样简化而不破坏对象关系？
- 面向真实研究员的第一轮试用应该如何设计，才能发现录入负担、检索失败和研究写作中的主要障碍？建议优先观察哪些少量指标？

### 13.2 数据模型与证据质量

- 机构关系、主办国别、出版机构、国际定位和资料研究对象的区分是否足够？哪些时间变化或身份变更会使现有模型困难？
- 原文、译稿、摘录、报告与专题的关系是否可持续？复用内容记录模型有哪些需要查代码才能确定的风险？
- 当前“题录快照＋实际摘录＋可选附件”的证据保存程度，是否满足第一轮研究试点？什么情况下才需要更完整的归档？
- 是否应优先建立来源更新与数据质量流程，而不是继续增加编辑功能？哪些数据缺口最先影响研究使用？

### 13.3 协作、权限与运行

- 全员共编目录译稿与作者授权个人成果的划分是否清晰？代交确认、历史作者认领、成员退出、错误恢复还缺哪些业务情形？
- 旧报告固定引用、当前读取权限与离线导出之间有哪些需要明确的制度取舍？请区分必须修复的行为缺陷与需要用户决定的规则。
- 本地实现进入小范围多人试用之前，哪些运行、账号、备份、源码管理和容量检查不可省略？哪些可以暂缓？
- 现有技术在什么使用量或功能条件下才有必要调整？请提出可观察的触发条件，而不是仅凭工具名称要求重写。

### 13.4 后续优先级与可借鉴方案

- 对第 10 节的候选顺序，你会保留、前移或删去什么？若下一轮只能做三件事，分别是什么，为什么？
- 哪些能力适合参考或复用成熟开源项目，哪些最好保持目前的小规模实现？如推荐具体项目或库，请核查官方资料，说明借鉴点、维护成本及许可证条件；不要把推荐等同于已经决定迁移。
- 如果建议增加 AI 辅助，请先说明要解决的具体任务、失败后果、人工核查方式及可验证收益，不把自动分析当作默认终点。

### 13.5 希望得到的审查输出

请按以下结构给出意见：

1. **整体判断：** 当前最有价值的基础、最严重的缺口，以及是否适合进入真实小规模试用。
2. **问题清单：** 按优先级排列，逐项说明问题、依据、影响、建议动作和验证办法；区分本文可证实的事实与尚待查证的推断。
3. **接下来三项工作：** 写出具体交付物和验收条件；同时列出暂时不建议做的事项及原因。
4. **必要澄清：** 最多五个确实会改变产品或实施方向的问题，优先提供选项和你的建议；已经确认的规则如需挑战，请明确说明理由与代价。
5. **需补充的材料：** 若需要源码、样本、页面截图或真实用户反馈才能判断，指出最小必要范围。没有这些材料时，不要声称已完成代码、安全或事实审计。

可以直接指出现有方案的问题，包括建设方当前建议的问题。请保留当前规模与资源背景，避免把完整企业级研究平台的所有能力都列为立即建设项。
