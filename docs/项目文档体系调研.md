# 项目文档体系调研

调研日期：2026-10-21。状态：历史调研，保留当时的讨论依据。2026-10-23 已制定生效的 [文档约定](agents/documentation.md) 和 [Matt 工作流](agents/workflow.md)，本调研不再充当当前写作或派工规则。

后续状态说明（2026-10-21）：用户随后授权先整理文档，已据此建立 [产品宪章](../PRODUCT.md) 和 [Agent 入口](../AGENTS.md)。下文保留调研时的事实与提议身份，其中“当前缺失”“未派工”“待讨论采用”等均描述当时阶段；当前规则、Grill 结论与阶段状态请读 [需求讨论记录](需求讨论记录.md)。本调研不作为并行的产品定义。

问题：哪些文档负责说明产品是什么，哪些文档负责约束 Agent，如何让新加入的 Agent 读懂项目，又避免文档重复和失效？

本次核查本地技能与一手公开资料，没有安装或更新技能，没有执行 setup 初始化或进入施工流程。下文区分“来源明确说了什么”和“本项目可如何理解”。

## 1. 核心发现

**没有查到 Matt Pocock 宣称所有优秀项目都必须具备同一套 Markdown 文件。** 他的官方仓库强调小型、可组合、可调整的技能；领域文档按实际形成的词义和决定建立，复杂工作才增加规格与任务拆分。不能把某套工具的模板目录当成普适合格证。[仓库说明][m-readme]、[领域建模][m-domain]、[工作流路由][m-ask]

据此可以推论：应先分清每种文档回答什么问题，再决定本项目需要哪些文件；不能为了“完整”先创建一批空模板。这个推论是本次调研的综合判断，不是 Matt 的固定文件清单。

## 2. Matt 系列技能实际规定了什么

| 核查对象 | 作者明确规定或说明的内容 | 对本次讨论的启发 |
| --- | --- | --- |
| `ask-matt` | 用于选择技能和工作流。讨论阶段由 `grill-with-docs` 澄清并保留领域记录；跨多个会话的建设走 `to-spec`、`to-tickets`；能在一个会话完成的工作可直接进入实现。[原文][m-ask] | 文档规模取决于交接与上下文需要；不是所有改动都要先写大规格。 |
| `setup-matt-pocock-skills` | 配置任务跟踪位置、可选的分诊标签、领域文档布局，并通过 `AGENTS.md` 或 `CLAUDE.md` 指向详细规则。支持本地 Markdown 任务；普通项目默认一个 `GLOSSARY.md` 加 `docs/adr/`。[原文][m-setup] | 它解决技能如何在项目中协作，并不替用户定义产品。调查这个技能也不等于本次要运行它。 |
| `domain-modeling` | `GLOSSARY.md` 只放领域词义，排除实现细节、规格和草稿。术语确定时记录；ADR 仅在决定难以撤回、缺少上下文会令人困惑、存在真实取舍三项同时满足时提出。文件按需建立。[原文][m-domain] | “机构”“期刊”“资料”“国际”应有稳定词义；不要把功能需求和技术选型都塞进术语表。 |
| `writing-for-agents` | 强调单一权威来源、明确的读取触发条件、按需展开细节、可判断的完成条件；删除重复、过期或不会改变行为的文字。仅部分任务需要的资料可由短入口指向。[技能原文][m-writing]、[作者文章][m-writing-article] | 约束文件需要具体且精简；产品定义只维护一份，其他入口引用它。 |
| `to-spec` | 将已讨论的内容综合为一份规格，发布到已配置的任务跟踪器；含问题、方案、用户故事、实现与测试决定、范围外事项。它不是重新决定需求的阶段，也不要求根目录必须存在 `SPEC.md`。[技能原文][m-spec] | 规格适合承接已经澄清的建设任务，不能把尚未确认的建议写成结论。 |

两个容易混淆的细节：

- Matt 的说明把 spec 定位为跨会话建设的决定快照；交付后可以弃用，长期有价值的领域语言和重要决定转入术语表或 ADR。**因此不能直接拿某次功能 spec 充当永久产品宪章。** 最后这句是适用于本项目的推论。[`to-spec` 说明][m-spec-doc]
- `docs/agents/domain.md` 的模板明确：领域文件不存在时继续工作，不要为了缺文件而预先补建；由领域讨论在有确定内容时产生它们。[模板][m-domain-consumer]

## 3. 其他一手实践的补充与边界

### GitHub Spec Kit：宪章、规格、计划的分工

Spec Kit 的 constitution 模板主要包含核心原则、约束、开发与审查流程、治理及修订信息；feature spec 模板描述用户场景、需求、边界情况与可衡量结果；plan 模板描述技术环境、结构、实施安排，并检查是否符合 constitution。[宪章模板][s-constitution]、[规格模板][s-spec]、[计划模板][s-plan]

**词义边界：** 用户在本项目所说的“宪法”，首先是“定义产品、让所有 Agent 知道项目干什么”的长期文档；Spec Kit 的 constitution 更偏项目原则和治理。两者可以互相借鉴，但不能因名字相同而用一份工程模板替代产品定义。这是本项目语境下的比较判断。模板里的示例原则也不能自动变成本项目的强制规则。

### Michael Nygard：ADR 保留重要决定的原因

Nygard 的原始文章主张用短文本记录对架构有显著影响的单个决定，交代背景、决定、状态与后果；决定被推翻后保留旧记录并标注被替代，帮助后来者理解“当时为什么这样做”。[原始文章，2011-11-15][adr-original]

Matt 的 ADR 模板更轻，可短至一个段落，额外章节只在有价值时增加。这表明 ADR 的重点是保留决定和理由，格式不必照搬成大表格。[Matt 的 ADR 格式][m-adr]

### Matklad：架构说明是给建设者的地图

Matklad 建议约一万到二十万行的开源项目增加简短的架构说明：说明大模块及其关系、稳定约束、边界与横切问题，帮助贡献者定位改动。这个建议有明确的项目规模语境，不能直接推出每个小原型都必须单建 `ARCHITECTURE.md`。[作者文章，2021-02-06][architecture]

## 4. 文档职责对照

以下是根据上述资料作出的职责整理，不是任何一位作者给出的统一强制清单。文件名可以适配项目已有约定。

| 文档或文档类别 | 主要回答的问题 | 是否立即单建 |
| --- | --- | --- |
| `README.md` | 项目入口在哪里，怎样运行和使用，进一步应读哪些文档？ | 优先维护现有入口；不能只靠启动说明承载完整产品定义。 |
| 产品定义／产品宪章，例如 `PRODUCT.md` | 为谁解决什么问题，产品边界、核心业务与长期原则是什么？ | 本项目用户已明确提出需要；具体内容应继续讨论确认。该命名是适配建议，不是 Matt 的规定。 |
| `AGENTS.md` | Agent 开工前读什么，遵守哪些协作与验收规则，何时查哪份详细文档？ | 可以作为短执行入口；不重复整份产品定义。具体加载机制由执行平台决定。 |
| `GLOSSARY.md` | 一个业务词究竟是什么意思，易混概念如何区分？ | 复用已有文件；只记录已经明确的领域词义。[依据][m-domain] |
| 功能规格，例如某功能的 `spec.md` | 这次要改变哪些行为，边界与验收条件是什么？ | 复杂、跨会话任务按需建立；不要求一份永久总 `SPEC.md`。[依据][m-spec-doc] |
| `docs/adr/*.md` | 哪个重要决定已被接受，为什么，后来是否被替代？ | 按重要决定逐条建立，避免把每个小选择都写成 ADR。[依据][m-domain]、[原始实践][adr-original] |
| 架构说明 | 当前系统有哪些主要部分和边界，建设者应从哪里理解它？ | 内容确有导航价值时维护；小项目可先复用现有施工说明的相关章节。[参考][architecture] |
| 计划、任务与进度记录 | 在确认的范围内先做什么，依赖什么，谁负责，进展如何？ | 随建设任务产生；沿用已有记录，避免另一套重复台账。[参考][m-ask]、[计划模板][s-plan] |

## 6. 本项目适配建议（待讨论采用）

### 6.1 已确认的目标

用户确认，宪法首先是定义产品的文档，使所有 Agent 知道项目干什么，也可包含必要约束。文件名和下面的文档分工仍是建议。当前只保存调研及讨论结果，没有建立生效的产品宪章或 Agent 规则，没有派发施工任务。

### 6.2 建议的最小常设结构

| 位置 | 本项目职责 | 当前状态及建议 |
| --- | --- | --- |
| `PRODUCT.md`，中文标题“研究中心资料平台产品宪章” | 长期产品定义的权威出处：目标、使用者、核心对象及关系、关键使用场景、首期边界、长期方向、产品原则与成功条件 | 当前缺失。建议下一步讨论并起草；名字是本项目建议，不是工具强制要求。 |
| `AGENTS.md` | 简短的 Agent 入口：项目定位摘要、产品文档位置、何时读取术语／规格／决策记录，以及协作和检查约定 | 当前项目根目录缺失。建议在文档分工和规则明确后建立，产品全文只放在 `PRODUCT.md`。 |
| [GLOSSARY.md](../GLOSSARY.md) | 统一“机构”“期刊”“资料”“成果”等已经确认的业务词义 | 已存在，继续维护。期刊国别与“国际”的口径未确认，保留待决状态。 |
| [README.md](../README.md) | 人的使用入口：启动、操作、限制，以及到产品和建设文档的导航 | 已存在，沿用；用简短摘要及链接介绍产品，详细定义维护在产品宪章。 |

这样新增的常设核心文件只有两份；已有文档继续承担原来的职责。该数量是根据本项目现状得出的建议，不是判断项目好坏的通用标准。

### 6.3 随任务按需增加的文档

- **功能规格**：某项需求讨论成熟后，保存行为、边界、异常情景与验收条件；若采用本地文档，可用 `docs/specs/<功能>.md`。例如来源目录改进的规格，须先解决期刊归属及国际属性，才能给建设 Agent 执行。规格可归档，但已确认且长期有效的产品规则应留在对应的长期文档中。
- **重要决定**：用 `docs/adr/<编号>-<主题>.md` 记录值得长期保留的取舍与理由；已有明确内容时才建立，不先填模板。
- **系统说明**：当前优先维护 [施工说明](施工说明.md) 中的系统结构与技术选择。复杂到现有说明难以表达时，再拆独立架构文档，并同步原入口，避免维护两份相同说明。
- **计划与进度**：沿用 `.planning/` 及项目现有任务记录；收到开工指令后再安排本轮任务与依赖，不并行创建另一份重复的 `TODO.md` 或 `ROADMAP.md`。
- **需求讨论和调研**：[需求讨论记录](需求讨论记录.md) 保留用户原意、已确认项与未决项；本文件保留参考依据。它们不是已批准功能规格，研究结论也不会自动成为产品约束。

### 6.4 产品宪章建议先回答的问题

1. 平台为谁服务，最重要的研究困难是什么，怎样判断建设有帮助。
2. 研究员与管理人员各能完成什么工作，谁对学术内容作判断。
3. 来源机构、期刊、原始资料和中心成果如何区分与关联；词义引用术语表。
4. 发现来源、积累资料、检索、编译、共享与纠错的主要使用路径。
5. 本期承诺的范围、当前未决定的事项、长期分析与成果产出方向。
6. 始终遵守的产品原则，例如出处可追溯、信息可纠正、界面符合对象含义、数据便于后续使用。
7. 产品定义怎样更新；产品目标或核心业务含义改变时如何回到讨论，具体技术在已确认范围内由建设方选择。

这些是待写内容的提纲，不能据此推定每个具体业务规则已经确认。首批拉脱维亚材料是已有试点基础，长期分析功能仍以原讨论的未决状态为准。

### 6.5 文档怎样真正被 Agent 使用

已核查 Codex 官方说明：它在开始一次运行时读取适用的 `AGENTS.md` 指令链；发现规则识别特定文件名，任意起名的产品 Markdown 不会因此自动成为指令入口。产品文件需要通过明确的引用与任务上下文被读取。[Codex 官方说明][codex-agents]

据此建议：首次接手项目时了解产品定义；涉及产品行为或数据含义时读取相关规格及术语；涉及重要旧决定时读取对应 ADR。给建设 Agent 派工时指出本次适用的文档版本和需求状态。正在进行的对话不能仅靠“磁盘新增了文件”就假定已掌握新规则。

官方关于 Agent 指引的文章同样强调根据具体任务读取相关资料，并持续清理过期约束。[官方文章][codex-context] 本项目可采用短入口加明确条件的方式，不要求每次小改动重复阅读全部历史。上述分工是适配建议，不是已部署的加载验证。

### 6.6 用来源目录问题检验分工

| 需要表达的内容 | 适合放在哪里 |
| --- | --- |
| 平台帮助研究员找到可追溯的来源与资料，界面信息应符合真实对象含义 | 产品宪章中的目标及产品原则（待讨论） |
| 机构与期刊是不同对象；机构可以主办期刊 | 现有术语表中的领域定义 |
| 机构详情不把 ISSN 显示成“待补充”；期刊按确认后的地域规则检索 | 本次功能规格与验收条件（尚未形成最终规格） |
| 期刊归属国家、国际属性如何定义 | 当前仍在需求讨论；确认词义后更新术语表，具体行为进入规格 |
| 为什么采用某个难以撤回的数据结构或归属规则 | 确有重要取舍时记录 ADR |

文件分工的目的，是让后续 Agent 能区分产品共识、当前任务、实现现状与仍未决定的问题。
