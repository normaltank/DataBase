# Markdown 写作与档案管理

生效日期：2026-10-23。修改项目 Markdown、调整文档职责或归档时读取。写作依据为本机安装的 Matt `writing-for-agents`；领域文件另按 `domain-modeling`，规格与任务分别按 `to-spec`、`to-tickets`。执行前读取对应技能原文，本文件只记录项目适配。

## 写作原则

- **单一出处。** 同一条规则在一个地方维护。其他文档用简短说明加链接；历史答复和已发布版本作为带日期的快照保留。
- **按需读取。** 入口使用“任务条件 → 文档 → 用途”，让 Agent 知道什么时候打开。AGENTS 保留通用约束与导航，详细步骤留在对应文档。
- **分清步骤与参考。** 操作按顺序写，每步有可检查的完成条件；定义、依据及例外放在同一主题下。只有不同任务确实需要不同内容时才拆文件。
- **写出可观察结果。** “能够保存，冲突时保留输入”比“完善编辑体验”可验收。区分已确认、建议、已实现与未验证，日期和证据范围跟随结论。
- **删去重复与过期指令。** 先查已有文档再新增。能从配置或代码直接查到的细目，只有确实帮助使用、交接时才记；不复制整份目录、函数清单或技能全文。
- **明确用词。** 使用术语表的名称，以正面指令描述目标。数据保护、权限等必要边界明确保留；业务规则的删改先核对用户原意。

这些是 Matt 的写作原则在本项目中的应用；以下文件名、归档方式及中文状态标识是项目约定，并非 Matt 要求每个项目具备的固定目录。

## 信息放在哪里

| 信息 | 唯一维护位置 | 其他文档怎样引用 |
| --- | --- | --- |
| 产品目标、边界、长期业务规则 | [PRODUCT](../../PRODUCT.md) | 规格引用规则并写本轮可验收行为 |

| 本轮行为、边界与验收设计 | `docs/specs/` 中对应规格 | GitHub 父任务保存带固定提交链接的发布快照 |
| 待办、阻塞关系、执行及关闭状态 | GitHub Issues | 文档只作带日期的阶段说明；同步方式见 [任务跟踪约定](issue-tracker.md) |
| 当前实现、架构边界与已知缺口 | [施工说明](../施工说明.md) | 实现事实可追到代码和当次验收 |
| 启动、使用、维护操作 | [根目录 README](../../README.md) | 产品文档链接使用说明 |
| 用户答复、决定出处及讨论历史 | [需求讨论记录](../需求讨论记录.md) | 生效规则指向 PRODUCT；历史提议保留当时身份 |
| 建设顺序建议及尚待细化的研究方向 | [长期愿景](../长期研究愿景与演进路线.md) | 已确认功能转入规格，路线保留摘要和入口 |
| 重要且有代价的取舍 | 按需建立 `docs/adr/` | 建立条件和格式见 [领域约定](domain.md) |

| 文档分类与历史查找 | [文档目录](../README.md) | 只导航，不再复制业务规则或验收正文 |

## 各类文档的写法

- **AGENTS：** 短项目定位、带触发条件的文档指针、所有任务都适用的约束。领域、流程和写作细则通过指针按需加载。
- **PRODUCT／README：** 前者解释产品，后者帮助实际运行和使用；按读者任务组织。它们是本项目保留的入口，不强套技能规格模板。
- **GLOSSARY／ADR：** 按 `domain-modeling` 的格式维护，见 [领域约定](domain.md)。已有充分内容才建文件。
- **功能规格：** 按 `to-spec` 写问题、方案、完整用户故事、实施决定、测试决定、范围外事项及补充说明。实施决定描述边界与接口，避免易过期的具体代码路径；有决定价值的原型片段按技能例外处理。
- **施工任务：** 按 `to-tickets` 写父任务、交付行为、验收条件及真实阻塞项。每项覆盖一条能独立演示的完整流程；任务正文能在新上下文独立执行。
- **需求讨论：** 记录用户问题、原答复或准确转述、确认状态、决定去向及未决项。新的决定追加后续记录，不把原来的未知改写成当时已知。
- **执行与验收：** 写实际改动、实际检查、结果及限制。开发自测、独立验收和历史结果分别归属；通过一次检查不等于持续通过，也不等于已部署。
- **调研／对外审查材料：** 标明资料截止点、已知范围、来源与推断。外部意见只有经本地核实的部分可以成为实现事实。

## 生命周期与归档

1. 新建前在文档目录和 Issues 查重，选定唯一维护位置。短任务直接使用已有入口；不为一次文档修正再建规格、三份计划或空模板。
2. 生效文档随规则变更更新；功能规格写明“草案”“已确认，待施工”或“已交付”及依据。用户确认不自动等于功能完成。
3. 规格发布和后续修订同步 GitHub 快照并记录版本；任务进度维护在 Issues，不再新增并行的长期待办台账。
4. 交付后，长期规则回到 PRODUCT／GLOSSARY，当前实现进入施工说明；规格、执行与验收作为当次历史证据保留。
5. 历史文件采用**原位归档**：保留路径、正文与原检查状态，顶部注明“历史档案”、后续结果和查找入口。旧端口、进程、暂停、待办或派工语句仅表示当时状态。
6. 旧 `.planning/` 与 `work/` 计划保留完成状态；新一轮进度使用 Issues。只有实际需要跨环境交接或保存较长证据时才新增相应记录。
7. 如必须迁移文件，先检查所有引用并一并修复；原始研究资料和未入库附件按已有授权边界保存。公开仓库中的本地证据链接须标明“仅原环境可查”，不能为修复链接上传受限材料。

## 文档交付检查

- 所有新增、修改的规则都有对应依据，当前指令与历史记录身份清楚。
- 仓库内链接和章节定位有效；本地专有证据与公共可访问文档分别检查，缺失证据如实记录。
- 本轮规格、Issue 快照和状态一致，业务规则未因改写文风而丢失。
- 版本差异、编码、空白检查通过；只改文档时做文档检查，应用测试结果只报告实际执行的部分。
