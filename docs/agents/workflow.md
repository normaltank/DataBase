# Matt 技能工作流

生效日期：2026-10-23；修订日期：2026-10-26。接收任务、拆分建设、派发实施或收尾时读取。本文件把已安装 Matt 技能接入本项目，不替代各技能原文。调用前读取对应 `SKILL.md`；路由不清楚时使用 `ask-matt`。

用户已要求改用 Matt 工作流。指挥 Agent 保留需求判断、任务编排与交付责任；后续施工使用当前任务的临时子 Agent。既有“建设Agent”“采集Agent”对话保留为历史参考；只有用户明确指定时才向这些对话派工。

## 按任务选择路径

| 任务 | 路径 | 完成依据 |
| --- | --- | --- |
| 业务含义或范围不清 | `grill-with-docs`，随讨论用 `domain-modeling` | 关键场景得到答复，词义和规则进入各自维护处 |
| 多个完整流程组成的新功能 | `to-spec` → `to-tickets` → `implement-spec` | 已确认规格、任务依赖、集成后的验收和审查 |
| 范围明确、一次上下文可完成的代码任务 | `implement` | 明确任务，TDD 验证、双轴审查及提交 |
| 文档整理、状态纠正、导航维护 | `writing-for-agents`，需要时读取领域或规格技能 | [文档交付检查](documentation.md#文档交付检查)；不额外造应用施工任务 |
| 新收到的缺陷或原始需求需分流 | 读取 `triage` 与 [标签约定](triage-labels.md) | 记录可执行范围或缺失信息；已生成的规格和任务不重复分流 |
| 本轮暴露了导航、约束或验证缺口 | `retro` | 根据实际会话提出或落实环境改进，不为小改动追加全套流程 |

接单时在现有任务或回复中说明所选路径。需要多个施工代理共同交付一份功能时，使用下述跨任务流程；一次可完成的小任务走 `implement`，纯文档维护走文档检查路径，不为套流程制造父子任务。已经批准的规格、拆分和验证边界直接沿用。

## 跨任务建设

1. **冻结范围。** `to-spec` 综合已有共识，写明范围、验收及验证边界，提交维护稿并发布固定版本的父任务。只有影响业务的未决项继续 Grill；完成条件是施工能从同一版本理解要交付的行为。
2. **发布任务图。** `to-tickets` 按可独立演示的完整流程拆分，每项覆盖所需数据、接口、页面及验证，写明真实阻塞关系。用户核对粒度及依赖后发布原生子任务；已有明确批准直接沿用。`ready-for-agent` 表示具备执行条件，不替代本轮派工授权。
3. **建立集成基线。** 指挥 Agent 记录集成分支、起始提交和固定审查基线，只派发依赖已满足的任务。指挥负责范围、调度、验收和发布；进入施工后，工作分支到集成分支的写入由合并代理串行执行。
4. **隔离施工。** 每项任务交给独立上下文、分支、工作树的施工代理。开始写入前核对基于已指定集成提交；基线不符时先保全已有改动，再调整基线。测试库和端口各自隔离。按 `tdd` 在约定的公开边界先复现失败，再实现并运行相关验证。
5. **同步后交接。** 施工代理交付前合入最新集成分支，解决冲突并重跑受影响的验证，提交最终成果；返回下节规定的交接证据。缺少同步或验证证据时，状态保持“待交接”，不能据此派发下游任务。
6. **由合并代理集成。** 单独调用 merger 子代理，核对交接证据后合入集成分支，返回集成提交与检查结果。指挥不代替 merger 执行工作分支集成。首次集成有实际提交后创建草稿 PR。已集成且验证通过的任务可解除下游施工依赖；Issue 关闭仍按最终 PR 交付处理，不等待关闭才启动下游。
7. **独立双轴审查。** 全部任务集成后运行完整检查，再按 `code-review` 启动独立的 Standards 与 Spec 两个只读审查代理，提供同一固定基线和待审提交。分别保留两轴发现及对应依据；施工者的自测不代替独立审查。
8. **单代理统一返修。** 存在审查发现时，把两份报告交给一个修复施工代理，在独立工作树内统一处理代码、测试及相关文档；指挥和原施工代理不再分别写入返修内容。修复仍经过同步交接和 merger 集成。交由原审查代理复核对应发现；不采纳的意见也记录理由并完成复核。新的改动或失败按实际影响补测，保留各轴结论。
9. **交付并清理。** 下节全部放行条件满足后，将草稿 PR 转为可审查；指挥按既有授权处理最终 PR 合并与发布，这与第 6 步的工作分支集成分别记录。按 [任务关闭约定](issue-tracker.md#交付与关闭)关闭已交付任务，归档已集成工作树并核查临时服务。未完成项继续留在 Issues。

## 交接与放行

以下证据写在对应 Issue／PR 的派工、交接或审查记录中，不另建长期台账。

| 环节 | 必须能核对的证据 |
| --- | --- |
| 派工 | 任务链接、固定规格版本、角色、工作树／分支、集成分支及起点 SHA、已满足依赖、验收条件与隔离测试资源 |
| 施工交接 | 最终提交 SHA、实际同步的集成 SHA、同步后验证命令与结果、未提交文件及真实剩余问题；检查无未说明的改动 |
| 集成 | merger 身份、接收前集成 SHA、施工提交 SHA、集成后 SHA、冲突处理及受影响验证；在任务中记录“已集成／可解除依赖” |
| 审查返修 | 固定比较基线和被审 SHA、两轴独立报告、每项发现的处置、修复提交与复核结论 |
| 最终放行 | 最终提交对应的必要检查、两轴无未解决阻塞项、当前文档与实现一致、PR／任务关联；有部署时另附备份、切换和实际运行核查 |

merger 接收时重新读取集成分支头：它必须与施工代理报告的同步 SHA 相同，且该 SHA 是交付提交的祖先，可用 `git merge-base --is-ancestor <同步SHA> <交付SHA>` 核查。集成分支已经前进时，退回施工代理同步并验证后重新交接；不用合并时临时修补代替交付前验证。一次只安排一个 merger 写入集成分支，其他代理继续在自己的工作树施工。

施工期间需要修订规格或项目说明时，也通过独立提交交给 merger 纳入；审查开始后由统一修复代理维护本轮交付文件。指挥继续处理业务决定和任务记录，审查代理保持只读。

上述同步 SHA、角色交接和审查发现处置记录是本项目为落实 Matt 流程增加的核对要求。工具或容量限制导致规定角色无法执行时，记录当前阻塞并推进其他已就绪工作；替代做法须说明原因及影响，保留偏离记录，不能把缺少的步骤标为已完成。历史任务保留当时真实过程。

## 上下文与派工

任务交给可调用的子 Agent 工具执行；用户的常驻聊天不是子 Agent 队列。技能要求并行时，在可用并发数内安排；有阻塞或共享资源冲突时顺序推进。

2026-10-24 用户最新指定：新唤起的子 Agent 优先使用 `gpt-6.1-sol`，思考强度 `high`（替代此前的 `max`）。派发时显式设置；已有子 Agent 无法直接调整时，以新上下文接回同一任务和工作树，保留未提交成果。所选模型不可用时说明实际限制，不把继承的模型当成已设置成功。

中断后若恢复工具不能指定或确认模型，先停止旧代理并核对已保存成果，再通过支持模型参数的新调用接手；不以恢复调用代替模型设置。汇报区分“调用已显式请求该模型”和“运行环境已确认实际模型”，缺少后者时不声称已核实。

派工优先提供 Issue、固定规格及既有证据的链接，不复制整段聊天历史；必要字段见[交接与放行](#交接与放行)。指挥核实实际交付后更新任务状态，不以代理一句“已完成”替代交接检查。

阶段边界按 `ask-matt/PHASE-BOUNDARIES.md` 判断是否继续当前上下文、使用子 Agent 或编写便携交接。保留仍有用的讨论；只有实际跨环境、跨目录或交给其他人员时才新增交接文档。更换模型后重新读取任务指针和完成条件，不从旧对话标题推定职责。

## 授权与验证

已授权的步骤和范围内技术选择直接推进。影响核心业务、内容权限或数据使用范围的问题由指挥 Agent 与用户澄清，同时继续独立工作。技能需要用户判断时先给出具体方案，并说明对应技能要求；不重复索取已有答案。

测试边界按 `to-spec`／`tdd` 事先明确，沿用已确认的规格与用户对技术选择的授权；有实质变化时说明新边界能验证什么及遗漏什么。纯文档工作执行文档检查，应用行为修改执行相关测试，界面或数据操作补充相应实际验收。

研究数据、采集或分析能力的任务按 [PRODUCT 的研究质量与复核条件](../../PRODUCT.md#研究质量与复核) 写明原始输入、选择范围、处理方法、独立检查方式及未知项。交付分别报告软件、资料、研究论证与跨人复用的证据；测试通过只关闭其实际覆盖的软件任务，不自动升级为研究能力已经验证。
