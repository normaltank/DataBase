# Matt 技能工作流

生效日期：2026-10-23。接收任务、拆分建设、派发实施或收尾时读取。本文件把已安装 Matt 技能接入本项目，不替代各技能原文。调用前读取对应 `SKILL.md`；路由不清楚时使用 `ask-matt`。

用户已要求改用 Matt 工作流。指挥 Agent 保留需求判断、任务编排与交付责任；后续施工使用当前任务的临时子 Agent。既有“建设Agent”“采集Agent”对话保留为历史参考；只有用户明确指定时才向这些对话派工。

## 按任务选择路径

| 任务 | 路径 | 完成依据 |
| --- | --- | --- |
| 业务含义或范围不清 | `grill-with-docs`，随讨论用 `domain-modeling` | 关键场景得到答复，词义和规则进入各自维护处 |
| 多个完整流程组成的新功能 | `to-spec` → `to-tickets` → `implement-spec` | 已确认规格、任务依赖、集成后的验收和审查 |
| 范围明确、一次上下文可完成的代码任务 | `implement` | 明确任务，TDD 验证、双轴审查及提交 |
| 文档整理、状态纠正、导航维护 | `writing-for-agents`，需要时读取领域或规格技能 | [文档交付检查](documentation.md#文档交付检查)；不额外造应用施工任务 |
| 新收到的缺陷或原始需求需分流 | 读取 `triage` 与 [标签约定](triage-labels.md) | 记录可执行范围或缺失信息；已生成的规格和任务不重复分流 |
| 本轮暴露了导航、约束或验证缺口 | `retro` | 根据实际会话提出或落实环境改进，不为小改动追加全套流程 |

## 跨任务建设

1. **澄清并形成规格。** 讨论与规格整理尽量留在同一上下文，保留决定原因；已确认答复直接沿用。`to-spec` 负责综合而非重新采访，使用术语表并明确验证边界。完成后发布到已配置的 GitHub 父任务。
2. **拆成完整流程。** `to-tickets` 每项穿过所需的数据、接口、页面与验证，写明真实依赖及验收。先展示具体拆分供用户核对粒度和阻塞关系，再按技能发布子任务；已有明确批准时直接沿用。`ready-for-agent` 表示任务具备执行条件，实际派工还要符合本轮授权。
3. **建立集成分支。** `implement-spec` 根据父任务和子任务建立依赖图，从合适基线建立集成分支。只派发阻塞项均已解决的任务，并记录固定审查基线。
4. **隔离实施。** 每个实施子 Agent 使用独立上下文、独立分支和工作树，以当前集成分支为起点。派发时提供任务链接、固定规格版本、工作树绝对路径和必要依据指针；避免复制整段聊天历史。开始写入前核对路径和基线，保留已有改动；独立工作树仍需隔离测试数据库和端口。
5. **验证与集成。** 实施子 Agent 按 `tdd` 在已约定的公开边界逐项验证行为，先失败再实现。完成前合入最新集成分支；合并子 Agent 将已验证提交合入集成分支，继续派发新解除阻塞的任务。
6. **审查完整结果。** 全部任务集成后，`code-review` 以固定基线分别启动 Standards（规范）与 Spec（规格）两个审查子 Agent，分别报告结果。修复发现的问题并完成相关验证；前端、权限和恢复等验收按规格执行，不能只靠代码阅读。
7. **交付与收尾。** 按 [任务关闭约定](issue-tracker.md#交付与关闭) 交付分支或 PR，更新实现及验收入口。工作树在成果已经保存和集成后清理；未完成任务保持可见。需要改进执行环境时再运行 `retro`。

## 上下文与派工

任务交给可调用的子 Agent 工具执行；用户的常驻聊天不是子 Agent 队列。技能要求并行时，在可用并发数内安排；有阻塞或共享资源冲突时顺序推进。

2026-10-24 用户最新指定：新唤起的子 Agent 优先使用 `gpt-6.1-sol`，思考强度 `high`（替代此前的 `max`）。派发时显式设置；已有子 Agent 无法直接调整时，以新上下文接回同一任务和工作树，保留未提交成果。所选模型不可用时说明实际限制，不把继承的模型当成已设置成功。

每份派工至少能回答：目标是哪条 Issue、适用哪个规格版本、在哪个工作树做、哪些任务已经完成、交付怎样验收。子 Agent 返回提交、实际验证和剩余问题；指挥方核实后更新任务状态。

阶段边界按 `ask-matt/PHASE-BOUNDARIES.md` 判断是否继续当前上下文、使用子 Agent 或编写便携交接。保留仍有用的讨论；只有实际跨环境、跨目录或交给其他人员时才新增交接文档。更换模型后重新读取任务指针和完成条件，不从旧对话标题推定职责。

## 授权与验证

已授权的步骤和范围内技术选择直接推进。影响核心业务、内容权限或数据使用范围的问题由指挥 Agent 与用户澄清，同时继续独立工作。技能需要用户判断时先给出具体方案，并说明对应技能要求；不重复索取已有答案。

测试边界按 `to-spec`／`tdd` 事先明确，沿用已确认的规格与用户对技术选择的授权；有实质变化时说明新边界能验证什么及遗漏什么。纯文档工作执行文档检查，应用行为修改执行相关测试，界面或数据操作补充相应实际验收。

GitHub 是任务状态的唯一台账；项目内规格是受版本控制的维护稿，父 Issue 是同版本发布快照。目录及状态见 [文档目录](../README.md)，文档如何归档见 [写作约定](documentation.md)。
